운영 신뢰성 인벤토리
— 자동매매 봇의 11개 안전장치와 6주간의 사고-패치 히스토리

2026-06-05 · KIS 모의투자 + Windows 데스크톱 환경 · 4계층 방어 구조 정리

한 줄 결과. 이 봇은 "Sharpe 가 높다" 보다 "6주간 실전 운영하면서 5번의 사고를 거치며 11개의 안전장치를 누적해 왔다" 가 더 강한 신호다. 정상 동작 시엔 안 보이지만, 비정상 상황에 처음으로 가치를 입증한다. 이 보고서는 그 11개 안전장치, 그것들이 박힌 자리, 그것들을 만들게 한 사고들을 한 자리에 정리한다.

1. 왜 reliability 가 portfolio 의 핵심인가

백테스트 수익률은 거의 모든 지원자가 자랑한다. 그런데 실제 인터뷰에서 면접관이 던지는 첫 질문은 거의 항상 "프로덕션에서 무엇이 잘못될 수 있나, 그때 어떻게 되나?" 다. 이 질문에 답할 수 있어야 "잘 짠 백테스트"와 "운영 가능한 시스템" 사이를 건널 수 있다.

이 봇은 6주간(2026-04 말 ~ 06 초) 실전 모의투자로 운영되며 의도치 않은 사고를 여러 번 겪었다. 매 사고마다 — 시초 데이터 공백, 매도 주문 누락, 손실 종목 미청산, 콘솔 깜빡임, PC 부팅 직후 봇 idle — 그 사건의 원인을 진단하고 코드에 안전장치를 박는 사이클을 반복했다. 그 결과 오늘 시점에 11개의 reliability 메커니즘이 들어있고, 각각이 어떤 사고를 막는지 명확하다.

2. 4계층 방어 구조 (defense in depth)

좋은 시스템은 한 곳에서 실패해도 다음 계층이 받아낸다. 이 봇의 안전장치들은 다음 4계층 중 하나에 속한다. 한 사고가 1계층을 뚫어도 2계층에서 잡히는 식.

도표 1. 4계층 방어 구조. 각 계층은 독립적이며, 한 계층이 뚫려도 다음이 받아낸다. 11개 메커니즘이 4계층에 분포.

4. Incident-driven 진화 — 6주간 5건의 사고와 패치

가장 강한 portfolio 신호는 "사고가 났고, 그 사고를 진단했고, 그 진단을 코드로 박았다" 의 사이클이다. 이 봇은 그 사이클을 다섯 번 돌았다.

차트 1. 사고-패치 타임라인. 각 사고는 며칠 내 진단·패치 사이클로 마무리됐고, 그 결과가 위 메커니즘 인벤토리에 박혔다.

사고 #1: 매도 주문 실패 silent drift (5/12)

증상. 매도 신호로 KIS 에 주문 보냈으나 KIS 가 reject. 봇의 state.positions 에선 매도된 걸로 처리됨 → 다음 iter 부터 그 종목이 "안 보이는" 상태로 KIS 계좌에는 그대로 남음 (phantom 의 반대 — missing).
진단. 봇이 state 만 믿고 KIS 잔고를 cross-check 안 함.
패치. 매 iter 시작 시 KIS balance 호출 → state.positions ↔ KIS holdings 비교 → 차이 시 KIS 기준으로 자동 정렬. run_dual_paper_trading.py#L521

사고 #3: 시초 22분 데이터 공백 (5/19~26)

증상. 매일 09:00~09:15 사이 KIS vts foreign-institution-total 엔드포인트가 500 또는 빈 응답. 이 22분이 외국인 갭매수 알파의 절반 이상을 차지하는 결정적 시간대 — 매일 가장 중요한 진입 기회를 놓침.
진단. KIS 모의서버 안정성 이슈, 우회 불가능. 그러나 직전 거래일의 마지막 가집계 응답은 disk 에 남겨둘 수 있음.
패치. PersistentPayloadCache 클래스 도입. 정상 응답이 들어올 때마다 disk 저장. 시초 빈 응답 시 직전 good payload (48h 이내) 로드 후 fallback signal 생성. 단 stale 데이터 위험을 위해 진입 임계 1.5배 강화 (false signal 위험 제한). foreign_inst_realtime.py#L181

사고 #4: 손실 종목 무한 보유 — 30위 외 사각지대 (5/26)

증상. 매수했던 종목이 가격은 빠지는데 외인+기관 매도 신호도 약해서 top-30 매도 리스트에 안 뜸. flow-only 매도 룰로는 잡을 수 없어 손실 종목을 무한 보유.
진단. Flow 가시성 한계 (top-30 만 보임) + flow 기반 매도가 유일한 청산 경로 — 가시성 사각지대에 들어간 포지션은 청산 불가.
패치. KOSPI 대비 underperform 룰 도입. 매수 시점 KOSPI 지수 저장 → 매 iter 비교 → 종목 수익률 - KOSPI 수익률 < -5% 이고 2영업일 이상 보유 시 강제 청산. "flow 와 무관한" 첫 청산 경로. run_dual_paper_trading.py#L405

사고 #5: 5분마다 콘솔 깜빡임 (6/01)

증상. 사용자 화면에 5분마다 콘솔 창이 깜빡임. 작업 중 시각적 방해.
진단. Watchdog 가 봇 생존 확인용으로 wmic, taskkill 같은 콘솔 프로그램을 호출하는데 CREATE_NO_WINDOW 플래그 없이 호출 → pythonw(windowless) 부모에서 자식 콘솔이 새 창을 띄움.
패치. 4곳의 subprocess.check_output / subprocess.run 호출에 creationflags=CREATE_NO_WINDOW 추가. 봇 자동복구 기능은 그대로 유지, 깜빡임만 제거. watchdog_dual_runner.py

사고 #6: PC 재부팅 → 봇 idle (6/04, 진행 중)

증상. 시스템 재부팅 후 봇이 자동 기동되지 않음. 사용자 로그인 + 다음 watchdog 5분 스케줄까지 ~수 시간 idle.
진단. Watchdog 스케줄 작업이 Logon Mode: Interactive only → 로그인 전엔 안 돔. 부팅 트리거도 없음. 더 깊은 문제: PC 자체가 죽으면 watchdog 도 죽음.
패치 (오늘 진행). ① Logon Mode 를 "Run whether user is logged on or not" 으로 변경, ② "시스템 시작 시" 트리거 추가, ③ 외부 모니터링 (PC 자체가 죽었을 때 알람) — 별도 검토.

6. 비전공자용 요약 (TL;DR)

  • 이 봇은 11개의 자동 안전장치를 가지고 있고, 그것들은 4계층(데이터 입력 / 주문 실행 / 상태 일관성 / 손실 통제) 으로 분산돼 있다.
  • 그 안전장치들은 책에서 베껴온 게 아니라 실제 사고 5건을 거치며 하나씩 박힌 것들이다. 사고 → 진단 → 패치 → 보고서 사이클이 git history 와 docs/ 에 남아있다.
  • 예를 들어 매일 09:00 KIS 모의서버가 빈 응답을 주는 패턴을 알아낸 뒤, 직전 거래일 데이터로 시초 22분을 메우는 fallback cache 를 직접 만들었다 (사고 #3).
  • 또 한 종목을 매도하려다 KIS 가 거절했지만 봇이 모르고 "팔린 줄로 알던" silent drift 사고가 났을 때, 매 iter 마다 KIS 실잔고와 봇 state 를 자동 정렬하는 sync 룰을 박았다 (사고 #1).
  • "백테스트 Sharpe 가 얼마"보다 "이 봇이 6주 동안 사고를 5번 겪고도 정상 운영 중" 이 더 강한 portfolio 신호다.
  • 아직 한계 있다 — PC 자체가 꺼지면 watchdog 도 못 돈다. 다음 단계는 외부 모니터링 또는 클라우드 마이그레이션.
