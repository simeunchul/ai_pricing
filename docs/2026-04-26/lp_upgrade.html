1. 무엇을 시도했는지 (배경 + 접근)

왜 LP 업그레이드인가

한화투자증권 디지털금융 JD 4축 중 "ETF LP 업무" 매핑이 약했음. 기존 etf_inav_arb.py 는 단방향 iNAV 평균회귀 — "LP 의사결정 모사" 라기엔 너무 단순. 실 LP 는 양방향 (bid + ask) 동시 호가 제출 + 재고 페널티 로 spread 수익 + 위험 관리.

접근 — Avellaneda-Stoikov (2008) 원논문 직접 구현

Avellaneda-Stoikov 가 마켓메이킹의 표준 모델. 핵심 수식: 

reservation_price = mid - q · γ · σ² · (T - t)        ← 재고 q 가 클수록 호가 skew
optimal_spread    = γ · σ² · (T - t) + (2/γ) · ln(1 + γ/k)
bid = reservation - spread/2
ask = reservation + spread/2

  q       : current inventory (signed)
  γ (감마): risk aversion (높을수록 재고 회피)
  σ       : asset 1-step volatility
  T - t   : remaining session time (∈ [0, 1])
  k       : order arrival intensity scale

3 가지 안전 메커니즘이 자동 작동:

  • 재고 페널티 (q · γσ²(T-t)): 재고 한 방향 쏠리면 reservation price 자동 skew → 자연 mean-revert
  • 시간 감쇠 ((T-t)): 만기/세션 임박 시 spread 좁아짐 → 위험 빠르게 줄이기
  • 주문 도착 강도 (k): 시장 활성도에 따라 spread 자동 조정

5. 비전공자용 요약 (TL;DR)

  1. 한화 JD 4축 중 "ETF LP 업무" 매핑이 약해서 기존 단방향 알고리즘을 Avellaneda-Stoikov (2008) 양방향 LP 알고리즘으로 업그레이드 (이게 마켓메이킹 표준).
  2. 핵심 수식: 호가의 중심 = mid 가격에서 보유 재고만큼 한 방향으로 밀고, 호가 폭 = 변동성 × 시간 + 주문 강도 함수. 재고 쏠리면 자동 mean-revert.
  3. 6개월 KODEX 200 일봉으로 백테스트 → 전부 큰 음수 손실. 이유는 알고리즘이 틀린 게 아니라 가정이 깨진 환경 (high-frequency 분봉이 아닌 일봉 + 강한 상승장).
  4. 그러나 이 실패에서 두 가지 수확:
    • (a) 알고리즘 자체: 양방향 호가, 재고 페널티, spread 계산 모두 정상 작동 검증
    • (b) compliance hook: Phase 1 에서 만든 audit log + HITL gate 가 LP 의 inventory 위반을 자동 감지·escalate. cross-cutting concern 설계 정당화
  5. 다음 단계: KIS API 모의투자 계좌 발급 후 분봉 (1분/5분) 데이터 + 횡보장 구간 으로 재검증. 분봉에서는 A-S 의 bid-ask spread 수익 메커니즘이 작동할 수 있음 (논문 결과는 1초 ~ 1분 봉 가정).
