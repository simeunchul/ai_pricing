KIS 다중 종목 + 섹터 ETF 확장

2026-04-27 (월) · ai_pricing 프로젝트 · 5-Layer 모노레포 Layer-E (Auto-Trading)

한 줄 결과. 단일 종목(KODEX 200)만 매매하던 KIS 모의투자 자동매매 봇을 5개 섹터 ETF 동시 운영으로 확장. 각 ETF 가 자기 바스켓을 가지도록 구조 리팩터, 바스켓 union 으로 quote 호출 1회만, 종목별 first-tick calibration 으로 절대 가격 차이 흡수. 내일 09:08 Windows 작업 스케줄러로 자동 시작 예약 완료.

1. 무엇을 시도했는지 — 배경 + 접근

1.1 배경: 단일 종목의 한계

어제까지 모의투자 봇은 KOSPI 200 ETF 한 종목 (069500 KODEX 200) 만 매매했습니다. 하루 종일 운영해본 결과, ETF 가격과 iNAV (이론가) 의 괴리가 ±2bps 안에서만 움직여서 매매 신호가 거의 안 나왔습니다 (BUY 1회, SELL 1회 정도). "폭발적으로 매매가 일어나는 환경"을 만들려면 두 가지 옵션이 있었습니다:

  • A. 같은 KOSPI 200 추종 ETF 5개 (KODEX/TIGER/KBSTAR/ARIRANG/KODEX 200TR) 동시 운영 — 같은 바스켓 공유. 운용사별 추적오차로 살짝 다른 dev 발생 기대.
  • B. 다른 지수/섹터 추종 ETF 추가 (코스닥150, 반도체, 2차전지, 헬스케어) — 바스켓이 ETF별로 달라짐. 코드 구조 변경 필요. 하지만 dev 변동 폭이 더 클 것으로 기대.

1.2 접근 순서

사용자가 "다양한 종목에서 기준이 만족하는지 테스트해보고 싶다" 고 해서 B 채택. 기존 코드는 모든 ETF 가 동일한 KOSPI 200 바스켓을 공유한다는 가정으로 짜여 있어서 ETF별 바스켓 dict 도입 + per-ETF 바스켓 페칭 로직 리팩터가 필요했습니다.

3. 어떻게 해결했는지 — per-ETF basket 도입

3.1 핵심 아이디어

ETF 별로 바스켓을 분리하되, quote 호출은 union (합집합) 한 번만 한다. 예: KODEX 200 의 삼성전자 + 반도체 ETF 의 삼성전자 = 같은 종목 → 1회 호출, 양쪽 ETF 가 결과를 공유. tick 당 quote 수 = unique 종목 수.

3.2 코드 변경 — ETF_BASKETS dict

ETF_BASKETS: dict[str, tuple[str, dict[str, float]]] = {
    "069500": ("KODEX 200",        KOSPI200_BASKET_TOP10),
    "229200": ("KODEX 코스닥150",   KOSDAQ150_BASKET_TOP10),
    "091160": ("KODEX 반도체",      SEMICONDUCTOR_BASKET_TOP10),
    "305720": ("KODEX 2차전지산업",  BATTERY_BASKET_TOP10),
    "266420": ("KODEX 헬스케어",    HEALTHCARE_BASKET_TOP10),
    ...
}

3.3 Main loop 의 union quote

# 모든 ETF 바스켓의 union — quote 1회만
all_constituents: set[str] = set()
for sym in symbols:
    all_constituents.update(ETF_BASKETS[sym][1].keys())

# 매 tick: union 만 페칭
for csym in all_constituents:
    sq = client.quote(csym)
    constituents[csym] = float(sq.get("output", {}).get("stck_prpr", 0))

# 종목별 sub-prices 추출 + 자기 바스켓 기준 calibration
for sym in symbols:
    own_basket = ETF_BASKETS[sym][1]
    sub_prices = {k: constituents.get(k, 0.0) for k in own_basket}
    inav = ss.inav_est.estimate(sub_prices)   # 자기 factor 적용

5. 비전공자용 요약 (TL;DR)

한 마디로: "한 종목만 매매하던 자동매매 봇이 5개 섹터 ETF 를 동시에 매매하게 됐다. 각 섹터마다 가격 측정 방식이 달라서 코드 구조를 바꿔야 했고, 그 과정에서 중복 호출을 제거해 효율도 올렸다."

왜 중요한가: 하나의 ETF 만 매매하면 그 ETF 의 가격이 안 움직일 때 자동매매 봇이 할 일이 없다. 섹터를 다양화하면 어느 섹터가 흔들리든 매매 기회가 생긴다. "하나의 시장만 보지 말고 여러 시장을 동시에" 라는 단순한 원리.

비유: 한 종류의 음식만 파는 식당 vs. 여러 메뉴를 파는 식당. 손님 취향이 그날그날 달라도 뭐든 팔린다. 다만 메뉴 늘리는 데 비용 (재료 = quote 호출) 이 들어서, 같은 재료가 여러 메뉴에 쓰이면 한 번만 사두는 (= union basket) 절약 트릭이 필요했다.

5.1 다음 단계 (예고)

사용자가 후속으로 던진 질문: "전 종목의 공정가치를 계산해서 임계점 기준으로 매수/매도하면 안 되나?" 이게 바로 quant value / statistical arbitrage 라고 불리는 본격 fundamental 전략 패러다임. 지금 코드는 ETF 의 iNAV 만 알지 개별 주식의 공정가치는 모름. 별도 모듈 (DCF or peer-relative or factor model) 로 확장 필요. 9주 스프린트 후반에 추가 보고서로 다룰 예정.

7. 용어 정리집 (Glossary)

용어한 줄 설명본문에서의 역할
ETFExchange Traded Fund. 주식처럼 거래소에서 사고팔 수 있는 펀드. 특정 지수나 섹터를 추종 이 보고서의 매매 대상. KODEX 200 / 코스닥 150 / 반도체 등.
iNAVindicative Net Asset Value. ETF 가 보유한 종목들의 가중평균 가격 = "이론가" ETF 시장가가 iNAV 보다 싸면 BUY, 비싸면 SELL 하는 차익거래 신호의 기준
바스켓 (basket)ETF 가 추종하기 위해 보유하는 구성 종목 + 가중치 묶음 iNAV 계산의 입력. 이전엔 KOSPI 200 하나만, 이번에 ETF별로 분리
calibration factor"바스켓 가중평균 × factor = ETF 가격" 이 되도록 첫 tick 에서 정하는 보정 상수 ETF별 절대 가격 차이 (예: 100k원 vs 20k원) 를 흡수해서 dev 측정을 0 에서 시작
dev (deviation)(ETF 시장가 − iNAV) ÷ iNAV. ETF 가 이론가보다 얼마나 비싸/싸졌는지의 비율 매매 신호 임계 (±1bps 등) 의 단위. dev 가 음수면 ETF 저평가 → BUY
bps (basis point)1bps = 0.01% = 0.0001. 금융에서 작은 비율 표시할 때 쓰는 단위 매매 임계 (enter=1bps = ETF 가 iNAV 대비 0.01% 어긋나면 진입)
union basket여러 ETF 의 바스켓을 합집합으로 합쳐 중복 종목은 한 번만 페칭하는 최적화 tick 당 KIS quote 호출 수를 55 → 47 로 줄임 (vts quota 보호)
EGW00201KIS API 가 초당 거래건수 (rate limit) 초과 시 반환하는 에러 코드 이를 피하려고 quote 사이 0.7s sleep + union 으로 호출 수 최소화
SAFE_OPEN / SAFE_CLOSE장 시작/마감 직후 10분 매매 차단 시간 (09:10~15:20 만 매매 허용) 변동성 폭증 구간에서 잘못된 calibration 으로 손실 방지
cronUnix 의 시간 기반 작업 스케줄러. "M H DoM Mon DoW" 5필드 표현식 사용 Claude Code 의 자동 실행 예약 메커니즘. Windows 작업 스케줄러와 비교됨
섹터 ETF특정 산업 (반도체, 배터리, 헬스케어 등) 종목들만 묶은 ETF KOSPI 200 (지수 추종) 보다 변동성 ↑ → dev 가 더 자주 임계 돌파 기대
